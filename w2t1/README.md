# w2t1 — простой агент на GigaChat с тремя инструментами

Первый шаг от «запрос к модели» к агенту: пользователь пишет запрос, модель
сама решает, нужен ли ей инструмент, программа выполняет обычную функцию
и возвращает результат модели, а та формулирует ответ.

```
пользователь → GigaChat (+ описание инструментов) → просьба вызвать функцию
            → функция в нашем коде (+ журнал вызовов) → результат обратно модели
            → текстовый ответ пользователю → снова приглашение ввести запрос
```

Модель не выполняет инструменты: она только просит вызвать функцию и передаёт
её аргументы. Выполняет функцию наш код, поэтому любое действие модели — это
вызов обычной функции в `main.py`.

## Инструменты

| Инструмент | Параметры | Возвращает |
|---|---|---|
| `roll_dice` | `sides` — число граней | случайное число от 1 до `sides` включительно |
| `current_time` | нет | текущие дата и время в часовом поясе машины |
| `decimal_to_hex` | `number` — целое число | шестнадцатеричную запись, например `0xff` |

Каждый инструмент — запись в кортеже `TOOLS`: имя, описание и схему параметров
модель получает из неё же, поэтому описание живёт рядом с функцией. Если описать
инструмент не словами, а только именем параметра, модель начинает выдумывать
аргументы — поэтому в описаниях есть примеры (`6`, `20`, `255`).

## Журнал вызовов

Каждое обращение к инструменту дописывается строкой JSON в `w2t1/tool_calls.log`
(файл копится между запусками, путь меняется флагом `--log`; в git не попадает —
это результат работы, а не исходник):

```json
{"time": "2026-11-13 01:53:53 MSK", "query": "Брось игральную кость с 8 гранями…", "step": 1, "tool": "roll_dice", "arguments": "{\"sides\": 8}", "result": "6", "error": ""}
```

| Поле | Что значит |
|---|---|
| `time` | время вызова с часовым поясом |
| `query` | запрос, в рамках которого вызван инструмент |
| `step` | номер шага агента по этому запросу |
| `tool` | имя инструмента |
| `arguments` | аргументы, которые прислала модель (`—`, если параметров нет) |
| `result` | результат; пуст, если была ошибка |
| `error` | текст ошибки, если инструмент не смог выполниться |

Пишется и неуспешный вызов: например, когда модель попросила несуществующий
инструмент или передала параметр неподходящего типа.

## Прогон

```powershell
python .\w2t1\main.py
```

Программа работает в режиме диалога: спрашивает запрос, гоняет его через цикл
агента и после ответа спрашивает следующий — пока не введёшь `/exit`.
Пустая строка пропускается, конец ввода (`Ctrl+D`, `Ctrl+Z` в Windows)
работает так же, как `/exit`.

По каждому запросу видно:

* шаги агента по ходу работы: какой инструмент и с какими аргументами вызван;
* ответ модели;
* сколько раз за этот цикл был использован каждый из трёх инструментов
  (ненулевые и нулевые — видно, что инструмент был доступен, но не понадобился).

После выхода подводится итог сеанса: число запросов и суммарные вызовы
по инструментам. Ошибка одного запроса не закрывает диалог — причина видна
сразу, следующий запрос можно задать снова.

Что проверить при запуске:

| Запрос | Чего ждём |
|---|---|
| «Сколько будет 17 умножить на 23?» | ни одного вызова — модель считает сама |
| «Брось игральную кость с 20 гранями…» | один вызов `roll_dice` |
| «Брось кость с 8 гранями и переведи число в шестнадцатеричную…» | два вызова подряд: `roll_dice`, затем `decimal_to_hex` с выпавшим числом |

Эти три запроса печатаются подсказкой при старте.

Флаги запуска:

| Флаг | Действие |
|---|---|
| `--model NAME` | другая модель GigaChat (по умолчанию самая дешёвая, `GigaChat`) |
| `--log PATH` | другой файл журнала вызовов |
| `--env PATH` | файл с ключом |
| `--no-cache` | переавторизоваться, минуя кэш токена |

Ключ `GIGACHAT_CREDENTIALS` берётся из того же `.env`, что и в прошлых задачах;
файл ищется от папки задачи вверх по дереву каталогов.

## Модель

Выбор модели не предусмотрен: по заданию агент работает на GigaChat с самой
дешёвой моделью — `GigaChat`, 65 ₽ за 1M токенов
(см. [`ai_models_prices.json`](../ai_models_prices.json)). Вызов функции она
поддерживает. `--model` оставлен для отладки, а не как выбор пользователя.

## Как устроен цикл

1. Модели уходят системная подсказка, запрос и массив `functions` с описанием
   трёх инструментов; режим `function_call: "auto"` разрешает ей выбирать
   функцию самой.
2. Если в ответе есть `function_call`, программа вызывает функцию, пишет журнал
   и добавляет в диалог два сообщения: ответ ассистента с просьбой и результат
   с ролью `function`.
3. Запрос повторяется — модель либо просит следующий инструмент (так запрос 3
   доходит до второго вызова), либо отвечает текстом.
3. Не более `MAX_STEPS = 6` шагов на запрос: модель, зациклившаяся на вызовах,
   иначе тратила бы токены бесконечно. Если лимит исчерпан, печатается
   «Ответ: не получен», а вызовы остаются в отчёте.

Ошибка одного запроса не роняет прогон: она печатается в его блоке, остальные
запросы выполняются дальше.

## Вывод

1. **Шаги и ответ** — по запросу: вызовы (`roll_dice({"sides": 8})
   → 8`), ответ, время, токены и счётчик вызовов по каждому инструменту.
3. **Экспорт** в корень проектов: `w2t1_<модель>_<ГГГГ-ММ-ДД>_<ЧЧ-ММ-СС>`
   — `.json` (описания инструментов, все шаги, ответы, токены) и `.csv`
   (разделитель `;`, `utf-8-sig`) для Excel.

## Ловушки, найденные на практике

* **Результат функции обязан быть валидным JSON.** API разбирает `content`
  сообщения с ролью `function` как JSON и отвечает HTTP 422 на голую строку:
  `invalid function result json string '0xff'`. Поэтому результат заворачивается
  в объект: `{"result": "0xff"}`, а ошибка инструмента — в `{"error": "..."}`.
* **`/v2/chat/completions` недоступен для пакета физлица** — отвечает 403.
  Используется `/v1/chat/completions` с полем `functions`; там же описан в
  документации весь сценарий с вызовом функций.
* **Модель может попросить неизвестный инструмент или передать строку вместо
  числа.** Проверка имени и разбор аргументов — в `run_agent`, ошибка уходит
  модели текстом, а не в исключение на весь прогон.
