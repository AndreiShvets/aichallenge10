# w4t1 — агент с инструментами MCP

Продолжение [`w2t2`](../w2t2): тот же агент с инструментами и памятью
разговора, но часть инструментов теперь приходит из внешнего MCP-сервера,
код которого в этом проекте отсутствует. Локальный инструмент из «дня 6» —
перевод целого числа в шестнадцатеричную систему; MCP-инструменты — файловые
операции официального filesystem-сервера внутри рабочей папки `workspace/`.

```
модель (один массив functions: local + MCP) → модель просит вызвать функцию
    → наш код: локальная функция или tools/call на MCP-сервер по stdio JSON-RPC
    → результат — тем же сообщением роли function → ответ модели
```

## Подключение к MCP

`mcp_client.py` — собственный клиент MCP поверх stdio на стандартной
библиотеке: поднимает серверный процесс `npx @modelcontextprotocol/server-filesystem`,
проводит рукопожатие `initialize`, запрашивает `tools/list`, вызывает
`tools/call`. Официальный SDK не используется — зависимости запрещены правилами
репозитория, а транспорт stdio — это JSON-RPC 2.0 построчно по stdin/stdout.

Доступ filesystem-сервера ограничен песочницей `w4t1/workspace/` (меняется
`--mcp-root PATH`). Первый запуск скачивает пакет из npm: нужны `node`/`npx`
в PATH и сеть.

## Запуск

```powershell
python .\w4t1\main.py --list-tools          # соединение + список инструментов, без модели
python .\w4t1\main.py                       # интерактивно, смешанный набор
python .\w4t1\main.py --print-request       # печатать тело первого запроса к модели
python .\w4t1\main.py --model GigaChat --mcp-root .\w4t1\workspace
```

Примеры смешанных задач (нужны и локальный, и MCP-инструмент):

```text
Прочитай файл note.txt и скажи, сколько в нём слов.
Переведи 255 в шестнадцатеричную систему счисления.
Переведи количество слов в note.txt в шестнадцатеричную систему и запиши ответ в файл report.txt.
```

Тело каждого запроса к модели пишется в `http.log` (см. `request_body.functions`);
`--print-request` дополнительно печатает тело первого запроса в консоль.

## Проверки

Соединение и список инструментов проверяются без модели и без ключей:

```powershell
python .\w4t1\main.py --list-tools
```

Протокол клиента и смешанный цикл агента проверяются без платных запросов:

```powershell
python -m unittest discover -s w4t1 -p "test_*.py" -v
```

Тест поднимает заглушку MCP-сервера (тоже по stdio JSON-RPC) и подменяет
клиент GigaChat: проверяются рукопожатие, список инструментов, вызов
`tools/call`, попадание схем обоих источников в тело запроса и маршрутизация
вызовов. Поведение реальной модели это не проверяет.

## Живые прогоны

Два прогона одной задачи («прочитай note.txt, переведи количество слов в hex,
запиши отчёт в report.txt») на базовой GigaChat, по 3 запроса каждый:

| Прогон | Вызовы инструментов | Итог |
|---|---|---|
| промпт «вызывай функцию» | `read_text_file`, `write_file` (оба MCP) | локальный инструмент обойдён: модель перевела число сама и ошиблась (`0x4` вместо `0x11`) |
| усиленный промпт «только через decimal_to_hex» | `decimal_to_hex` (local), `read_text_file`, `write_file` (MCP) | оба источника в одном прогоне; но число слов модель сосчитала до чтения файла и неверно (24 вместо 17 → `0x18`) |

Вывод: транспорт и маршрутизация работают одинаково для обоих источников;
ошибки — не в инфраструктуре, а в самой модели. Во-первых, она может молча
решить подзадачу без инструмента и ошибиться. Во-вторых, точный подсчёт слов —
это работа без инструмента (счётчика слов в наборе нет), и модель делает её
ненадёжно. Детерминированный смешанный сценарий требует, чтобы число приходило
из файла явно, а не считалось моделью.

## Ответы на вопросы задания

**Как модель различает локальный инструмент и MCP-инструмент?**
Никак. В запрос уходит один массив `functions` (см. `McpConnection.schemas`):
у обоих источников одинаковая форма `{name, description, parameters}` —
у MCP это `inputSchema` из `tools/list` без преобразований. Модель выбирает
инструмент по имени и описанию и не знает, где он выполняется. Различие
возникает в нашем коде после ответа модели: `run_agent` ищет имя в
`LOCAL_TOOLS_BY_NAME` (функция Python) или в инструментах соединения
(`tools/call` процессу сервера).

**Что именно изменилось в коде при переходе на MCP?**
Цикл агента, память разговора и формат результата не изменились вовсе —
контракт tool-calls тот же. Добавились: (1) `mcp_client.py` — подъём
серверного процесса, JSON-RPC с рукопожатием и ожиданием ответа по id;
(2) `connect_mcp` — соединение и `tools/list` на старте, схемы берутся
у сервера, а не пишутся руками; (3) `call_mcp_tool` — ветка маршрутизации,
которая вместо вызова функции отправляет `tools/call` и разворачивает
текстовые блоки ответа; (4) `McpError` не роняет прогон — ошибка инструмента
уходит модели как результат функции. Локальные инструменты и их вызов
остались как в w2t2.

**Зачем нужен MCP?**
Чтобы не писать и не сопровождать инструмент в каждом агенте. FileSystem-сервер
написан один раз сторонними разработчиками, и любой агент на любом языке
получает готовые файловые операции, запросив список у сервера: в этом проекте
ни одной файловой функции мы не написали. MCP даёт единый протокол вместо
своего транспорта на каждую связку «агент — инструмент», изоляцию (инструмент
живёт в отдельном процессе с собственной песочницей путей) и заменяемость:
 filesystem можно сменить на git, sqlite или memory без единого изменения
цикла агента — массив `functions` просто пополнится с `tools/list`.

## Файлы

| Файл | Что делает |
|---|---|
| `mcp_client.py` | клиент MCP поверх stdio: initialize, tools/list, tools/call |
| `main.py` | агент w2t2 + смешанный набор, `--list-tools`, `--print-request` |
| `test_mcp.py` | unittest на заглушке сервера и подменном клиенте модели |
| `gigachat_client.py`, `certs/` | копии из [`w2t2`](../w2t2) (самодостаточность задачи) |
| `workspace/` | песочница filesystem-сервера; в git не попадает |
