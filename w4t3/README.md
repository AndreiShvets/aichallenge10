# w4t3 — планировщик и фоновые задачи

Приложение по расписанию дёргает инструменты MCP-сервера: собирает снимок
трекера, сохраняет его в журнал, напоминает про открытые задачи и раз в
несколько запусков выдаёт сводку за всё накопленное время.

```
scheduler.py ──MCP/HTTP──> server.py
   │  fetch_snapshot  — опрос трекера (каждый вызов сдвигает состояние)
   │  save_run        — запись снимка и напоминания в runs.json
   │  read_runs       — все записи периода
   ▼
aggregate.py — цифры по всем записям (не по последней)
summary.py   — текст сводки через GigaChat по готовым цифрам (--summary)
```

## Состав

| Файл | Что делает |
|---|---|
| `server.py` | MCP-сервер поверх HTTP с тремя инструментами; журнал — JSON-файл |
| `store.py` | журнал запусков: запись дописывается, чтение по периоду и виду |
| `tracker.py` | mock-трекер: статусы детерминированно меняются от опроса к опросу |
| `aggregate.py` | сводка без сети: средние, смены статусов, счётчики |
| `scheduler.py` | цикл по расписанию, сохранение, сводка каждые N запусков |
| `summary.py` | текст сводки через GigaChat; без `--summary` не вызывается |
| `mcp_http_client.py`, `gigachat_client.py`, `certs/` | копии из w4t2 |
| `test_snapshot.py` | 18 проверок без сети и модели |

## Инструменты сервера

| Инструмент | Параметры | Что делает |
|---|---|---|
| `fetch_snapshot` | `status` необязательно | опрос трекера; состояние меняется от вызова к вызову |
| `save_run` | `kind` (`snapshot` / `reminder`), `data` | дописывает запись с номером и временем |
| `read_runs` | `from`, `to` (`YYYY-MM-DD`), `kind` необязательно | все записи периода |

Журнал `runs.json` лежит рядом с `server.py` (путь меняет `--runs`). Ошибки
предметной области (неверный вид, битая дата) возвращаются результатом с
`isError`.

## Запуск

```powershell
python .\w4t3\server.py                     # окно 1: сервер и журнал
python .\w4t3\scheduler.py --interval 10 --report-every 3   # окно 2: планировщик
python .\w4t3\scheduler.py --interval 10 --report-every 3 --summary   # с текстом через GigaChat
```

Планировщик работает, пока его не остановят Ctrl+C. Флаги: `--mcp-url`,
`--interval` (секунды между запусками), `--report-every` (сводка каждые N
запусков), `--max-runs` (остановиться после N запусков), `--summary`.

Для `--summary` ключ `GIGACHAT_CREDENTIALS` берётся из `.env` выше по дереву
(образец в `.env.example`).

## Проверки

```powershell
python -m unittest discover -s .\w4t3 -p "test_*.py" -v
```

Без модели: накопление записей между сохранениями, фильтр периода и вида,
конец периода датой включает весь день, битый журнал — ошибка; агрегация
берёт все снимки, а не последний; смены статусов считаются между соседними
снимками; инструменты регистрируются со схемами; сводка получает цифры из
агрегации (через заглушку клиента).

Ручной прогон: 4 запуска подряд с интервалом 1 с и сводкой каждые 2 запуска.
Журнал накопил все 8 записей, сводка после четвёртого запуска считала по всем
8, а не по последней паре.

Живой прогон сводки: три запуска и одна сводка через GigaChat, 1 запрос к модели.

## Ответы на вопросы задания

**Что делает планировщик без вашего участия?** Цикл внутри `scheduler.py`
через `time.sleep` вызывает инструменты по расписанию. Каждый запуск пишет
снимок и напоминание; каждые N запусков читает журнал и считает сводку.

**Почему отчёт собирается из всех запусков?** `read_runs` возвращает записи за
весь период с момента старта планировщика. `aggregate` идёт по всем снимкам,
поэтому среднее и смены статусов отражают весь период.

**Почему напоминание не делает второй опрос?** `fetch_snapshot` двигает
состояние трекера. Второй опрос в том же запуске дал бы другой момент, и
снимок с напоминанием расходился бы.

**Почему сводку считает код, а не модель?** Модель пересказывает числа из
промпта и не считает сама. В промпте только цифры из `aggregate`, поэтому
выдуманной статистики в тексте быть не может.
