# w2t3 — агент с памятью и учётом токенов

Продолжение [`w2t2`](../w2t2): тот же агент с инструментами и памятью
разговора, который теперь считает, сколько токенов стоит каждый запрос.
Вопрос задачи — насколько дорого обходится длинный разговор: вход платится
за всю историю на каждом шаге цикла, и чем беседа длиннее, тем дороже
следующий вопрос, — а в какой-то момент история перестаёт влезать
в контекст модели.

```
запуск → читает history.json и лимит контекста модели
       → /fill (если нужно): история наполняется до лимита
       → запрос пользователя
       → GigaChat (вся история + описание инструментов) → просьба вызвать функцию
       → функция в нашем коде (+ журнал вызовов) → результат обратно модели
       → ответ + расход токенов: за цикл, за сеанс, за историю
       → запрос и ответ дописываются в history.json
       → следующий запрос … до /exit
```

Три инструмента (`roll_dice`, `current_time`, `decimal_to_hex`), журнал
вызовов, HTTP-лог, `/clear` и формат `history.json` перенесены
из `w2t1`/`w2t2` без изменений —
подробности в [`w2t1/README.md`](../w2t1/README.md)
и [`w2t2/README.md`](../w2t2/README.md). Новое здесь — расход токенов,
команды `/limits` и `/fill`, флаг `--limit`, лимит контекста модели
и два новых инструмента: `readme_words` и `fetch_url`.

## Инструмент `readme_words`

Четвёртый инструмент собирает текст из случайных слов файла `w2t3/README.md`:

| Параметр | Что значит |
|---|---|
| `lines` | сколько строк собрать (целое число больше нуля) |

Возвращает строку, где на каждую строку приходится 16 случайных слов,
а начинается она с порядкового номера:

```
И вот еще вопрос 1: модели. истории. токенов сравнить ``` фо…
И вот еще вопрос 2: процентов запуска --limit переопределяет…
```

Каждая строка заканчивается переводом строки. Слова берутся из README без
повторов и в случайном порядке (`random.sample`), поэтому текст выглядит
как связный, а по смыслу его нет — это заполнитель для проверки длины
контекста, а не источник ответов.

Ограничения: в README должно хватать разных слов (`lines × 16`), `lines`
меньше единицы и отсутствие файла — ошибка инструмента, а не падение
прогона: ошибка уходит модели, диалог продолжается.

## Инструмент `fetch_url`

Пятый инструмент скачивает страницу или файл по адресу и возвращает модели
её текст — чтобы можно было сказать «проанализируй страницу по адресу …»
или «перескажи кратко, о чём тут речь …».

| Параметр | Что значит |
|---|---|
| `url` | полный адрес: `http://`, `https://` или `file://` |

Возвращается не HTML, а чистый текст: выкидываются `script`, `style`,
`noscript`, `template`, `nav`, `header`, `footer`, из блоков (`p`, `div`,
`li`, заголовки, таблицы) текст разбивается на строки, пробелы и пустые
строки схлопываются, HTML-сущности раскрываются. Заголовок `<title>`
идёт первой строкой:

```
Заголовок: Тестовая страница

Заголовок статьи
Первый абзац текста.
пункт 1
пункт 2
```

Локальный файл читается через `file://` — так модели можно подсунуть
собственную страницу, сохранённый текст, CSV-выгрузку или JSON-результат:

```
Скажи, о чём эта страница: file:///home/user/page.html
Сколько запросов в этой выгрузке: file://w2t2_GigaChat_2026-11-13_03-05-52.csv
```

Адрес с ведущим слешем абсолютный, без слеша — относительный от текущего
каталога (`file://page.html`, `file:a.txt`). Без этой развязки привычный
`url2pathname` принимал бы `file://page.html` за хост `page.html` и
открывал бы пустой путь. Кириллица и пробелы в имени работают — и в виде
`%D1%82…`, и как есть.

Файл отдаётся модели как обычный текст, без разбора по формату: CSV придёт
строками с `;`, JSON — как есть, с `\n` между элементами. BOM (`\ufeff`)
в начале CSV остаётся символом в первой ячейке заголовка — модели это видно,
но на смысл не влияет. Если у локального HTML-файла нет `<title>`, первой
строкой будет сам адрес.

Кодировка: у страницы — из ответа сервера, затем UTF-8 и cp1251; у локального
файла первые две те же, а в конце Latin-1 — он не ошибается никогда, поэтому
файл в чужой кодировке будет прочитан хоть как-то, а не отвергнут.

Ограничений по размеру нет — ни на длину страницы, ни на размер файла.
Плата за это — контекст: текст возвращается модели целиком, поэтому длинная
страница съедает входные токены, а если она вместе с результатом функции
превышает лимит модели, запрос получает отказ `422`.

Ошибки — результат шага, а не падение прогона:

| Что случилось | Что увидит модель |
|---|---|
| `ftp://`, `data:`, пустой адрес | «Адрес … не поддерживается: нужен http:// или https:// или file://» |
| файла нет или нет прав | «Не удалось прочитать файл …» |
| сервер ответил 404/403/500 | «Страница ответила HTTP 404: Not Found» |
| нет сети, DNS или таймаут 20 с | «Не удалось скачать …» |

В `tool_calls.log` результат пишется обрезанным (первые 300 символов
и полная длина), а не целиком: журнал нужен для разбора вызовов,
а не как копия страниц. Так же обрезаются аргументы вызова — адрес
с токеном в параметрах не должен осесть в журнале целиком.

## Расход токенов

После каждого ответа печатается блок токенов:

```
Токены:
  запрос: 1204 вход + 38 выход = 1242 за 2 обр. (вход — только некэшированная часть)
  ответ модели: 31 выход (ещё 7 — на просьбы вызвать функцию)
  шаг 1: вход 702, оценка 690 (-2%)
  шаг 2: вход 1204, оценка 1180 (+2%)
  оценка входа по шагам: первый -2%, последний +2%
  история разговора: ~1180 токенов (0.9% лимита 130048), осталось 128868
  следующий вопрос уйдёт с историей: ~1240 токенов (1.0% лимита 130048), осталось 128808
  в истории разговора: 3 обменов, ~1240 токенов (1.0% лимита 130048), осталось 128808
```

«обр.» — обращения к модели: сколько раз за цикл программа сходила в API
(один вызов инструмента — это два обращения). Числа здесь условные: живой
прогон даёт свои.

| Строка | Что означает |
|---|---|
| `запрос` | сумма по шагам цикла: сколько стоил этот запрос целиком |
| `ответ модели` | сколько из выхода пришлось на текст ответа, а сколько на просьбы вызвать функцию |
| `шаг N` | вход и оценка того же шага — сравниваются только внутри одного шага |
| `оценка входа по шагам` | два числа: расхождение на первом шаге и на последнем |
| `история разговора` | текущий размер контекста: токены, доля лимита и остаток |
| `следующий вопрос уйдёт с историей` | то же с добавленной парой «запрос–ответ»: столько уйдёт модели на следующем вопросе |
| `в истории разговора` | строка после сохранения обмена: история выросла и вот её новый размер и остаток |

Токены считаются дважды. **Факт** — `usage` из ответа API (это и есть деньги).
**Оценка** — своя формула `estimate_tokens`, потому что до запроса API ничего
не сообщает, а знать, влезет ли история в лимит, надо заранее.

Сравнивать оценку с фактом можно только внутри одного и того же шага.
После вызова инструмента в сообщения уходит его результат (от сотен байт
до сотен килобайт у `fetch_url`), и вход следующего шага — уже другой запрос.

Ошибка одного запроса не закрывает диалог: причина печатается в его блоке,
следующий запрос можно задать снова.

## Оценка токенов

Точного токенизатора GigaChat в стандартной библиотеке нет, поэтому оценка
по символам:

* кириллица — `ESTIMATE_CHARS_PER_TOKEN = 5` символов на токен,
  латиница и цифры — 4;
* плюс `TOKENS_PER_MESSAGE = 4` служебных токена на каждое **сообщение**;
  описания инструментов считаются без этой надбавки — они не сообщения.

Насколько это точно — можно посмотреть на собственном прогоне: на шагах,
где API отдал весь вход, факт давал около **1.15 от оценки** (медиана
по 16 шагам), то есть формула осторожна и оценивает вход с небольшим запасом.
Прежняя версия делила кириллицу на 3, и ошибка была в полтора-два раза.

**`prompt_tokens` — это не всегда весь вход.** GigaChat в разных запросах
отдаёт то весь вход, то только некэшированную часть (в `http.log` второго
прогона при 5775 символах истории вход был 330 токенов, а при 6128 — 2471).
Поле `precached_prompt_tokens` тоже нельзя читать как длину кэша префикса:
оно плавает от 2 до 2847 токенов независимо от текста. Отсюда правило:
оценка проверяется по шагам, где кэша нет, а не по одному проценту.

## Команды диалога

| Команда | Действие |
|---|---|
| `/exit` | выйти; история остаётся на диске, следующий запуск её подхватит |
| `/clear` | забыть разговор: `history.json` удаляется, беседа начинается заново |
| `/limits` | расход токенов: сеанс, история целиком и каждый её обмен |
| `/fill [N]` | наполнить историю: без аргумента — до лимита модели, с числом — ровно N слов |
| `/help` | справка: все команды диалога и параметры запуска |
| пустая строка | пропускается |

Конец ввода (`Ctrl+D`, `Ctrl+Z` в Windows) работает так же, как `/exit`.

### `/limits`

```
Токены
  модель: GigaChat, лимит контекста 130048
  история разговора: ~1180 токенов (0.9% лимита 130048), осталось 128868
  сеанс: 1204 вход + 38 выход = 1242 за 1 запросов (это трата и деньги)
  из выхода 31 — текст ответов, 7 — просьбы вызвать инструменты
  история #1: вход 702 + выход 12 = 714, оценка входа 690 (-2%)
      шаг 1: контекст ~690, факт 702 (+2%), до лимита 129358 → roll_dice
      шаг 2: контекст ~720, факт 700 (-3%), +30 к шагу выше, до лимита 129328
  всего в истории: 1 обменов
```

Расход по каждому обмену берётся из `history.json` и переживает перезапуск:
сеанс считает только текущий запуск, история — все обмены в файле.
Числа в примере условные, набор строк — настоящий.

**Строки `шаг N` — это и есть размер контекста, ушедшего в модель.** Их два
на каждом шаге:

| Поле | Что значит |
|---|---|
| `контекст ~N` | наша оценка полного входа: история, запрос, описания инструментов и (со второго шага) результат функции. Именно это число растёт от шага к шагу |
| `факт N` | `usage.prompt_tokens` того же шага; если вход не кэшировался, он совпадает с полным, а если кэшировался — это только некэшированная часть, то есть меньше |
| `(+N%)` или `(-N%)` | расхождение факта с оценкой внутри одного шага |
| `+N к шагу выше` | насколько вырос контекст по сравнению с предыдущим шагом: обычно это ответ модели и результат функции |
| `до лимита N` | сколько токенов осталось до лимита модели с этого шага |
| `→ инструмент` | на этом шаге модель просила вызвать функцию |

### `/fill`

Сценарий «разговор длиннее лимита модели» иначе требовал бы тысячи введённых
запросов, поэтому история наполняется залпом слов-заполнителей. Заполнитель
пишется как обычный прошлый обмен (длинный запрос и короткий ответ агента),
и дальше это нормальный длинный разговор:

```powershell
python .\w2t3\main.py --fill 5000     # 5000 слов сразу после запуска
```

```
/fill          наполнить до лимита модели (~89 000 слов по текущей оценке)
/fill 5000     ровно 5000 слов — для отладки, минимум 100
```

Число слов до лимита считается той же формулой `estimate_tokens`, что и вся
остальная оценка, по настоящей строке-заполнителю. Отдельного коэффициента
для заполнителя нет: прежний (два токена на слово) был догадкой и ошибался
почти в три раза.

Обращение к модели при заполнении одно, и нужно оно для того, чтобы увидеть
факт его `usage` рядом с оценкой. Сколько на самом деле слов влезет — покажет
следующий обычный запрос: при переполнении модель ответит отказом `422`,
при успехе — строкой о доле лимита в отчёте.

## Файл истории

Обмен с `fetch_url` попадает в модель целиком — запрос, вызов с полученным
текстом и ответ, — поэтому фраза «а что сказано во втором абзаце?» уже
работает без повторного вызова. Плата — контекст: текст страницы
пересылается в каждом следующем запросе до `/clear`.

Путь по умолчанию — `w2t3/history.json`, меняется флагом `--history`.
В git файл не попадает: это результат разговора, а не исходник. Формат
тот же, что в `w2t2`, плюс два поля с расходом токенов на обмен:

```json
{
  "version": 1,
  "started": "2026-11-13 03:40:11 MSK",
  "saved": "2026-11-13 03:40:18 MSK",
  "turns": [
    {
      "at": "2026-11-13 03:40:18 MSK",
      "query": "Сколько будет 17 умножить на 23? Ответь одним числом.",
      "answer": "391",
      "tools": [],
      "steps": [],
      "tokens": {
        "prompt": 702, "completion": 12, "total": 714,
        "answer": 12, "functions": 0, "context": 690
      },
      "usage": [
        {"step": 1, "prompt": 702, "completion": 12, "cached": 0,
         "estimated": 690, "function": ""}
      ]
    }
  ]
}
```

| Поле | Что значит |
|---|---|
| `tokens.prompt` / `completion` / `total` | расход по `usage` за весь цикл этого обмена |
| `tokens.answer` | сколько выхода пришлось на сам ответ |
| `tokens.functions` | сколько выхода ушло на просьбы вызвать функцию |
| `tokens.context` | оценка входа первого шага: сколько ушло модели вместе с запросом || `usage[]` | то же по каждому обращению к модели: шаг, вход, выход, кэш, оценка |

Остальные поля (`version`, `started`, `saved`, `turns[]`, `at`, `query`,
`answer`, `tools`, `steps`) описаны в [`w2t2/README.md`](../w2t2/README.md).
В модель эти поля не уходят: ей нужны только тексты `query` и `answer`.

## Лимит контекста

Лимит — свойство модели, а не разговора, и в ответе API его нет. `130048`
токенов узнаны опытом: запрос с 200 000 слов заполнителя получил отказ
`HTTP 422 «maximum allowed context is 130048»`. Поэтому лимит задан
константой `DEFAULT_MODEL_LIMIT` и переопределяется флагом `--limit`.

Процент лимита — это **оценка** по формуле выше, а не факт: точное число
покажет только ответ модели или его отсутствие.

## Экспорт

После выхода результаты сеанса пишутся в корень проектов:
`w2t3_<модель>_<ГГГГ-ММ-ДД>_<ЧЧ-ММ-СС>` — `.json` (описания инструментов,
все шаги, ответы, токены по каждому обращению, `estimated_context`,
`estimated_prompt`) и `.csv` (разделитель `;`, `utf-8-sig`) для Excel.
Артефакты прогонов в git не попадают.

## Прогон и проверка

```powershell
python .\w2t3\main.py
python .\w2t3\main.py --fill 5000        # история наполнена до первого вопроса
python .\w2t3\main.py --history tmp.json --limit 4000   # свой файл и свой лимит
```

Три сценария задания:

1. **Короткий диалог.** «Сколько будет 17 умножить на 23? Ответь одним числом.»
   и «А если это число умножить на 2? Ответь одним числом.» — второй ответ
   опирается на первый (391 → 782), а вход второго запроса больше первого
   на размер первого обмена.
2. **Длинный диалог.** 8–10 обменов подряд: видно, как строка
   «история разговора» растёт с каждым обменом и как растёт цена запроса.
3. **За лимитом.** `/fill` доводит историю до лимита, после чего следующий
   запрос либо проходит, либо получает отказ `422` — отказ печатается,
   диалог продолжается, `/clear` возвращает к короткой истории.

Кроме токенов, стоит проверить:

* `/limits` после перезапуска: расход по истории на месте, сеанс — с нуля;
* `/clear`: файл исчезает, счётчики истории обнуляются;
* `readme_words`: «Попроси инструмент readme_words собрать 3 строки» —
  в ответе три строки по 16 слов с номерами 1–3;
* `fetch_url`: «Проанализируй страницу https://example.com» — один вызов
  `fetch_url`, следом пересказ; то же с `file://` на локальный файл;
* **Оценка входа третьего запроса** — сходится ли она с фактом после
  двух обменов с большим ответом;
* расхождение оценки с фактом остаётся в пределах десятков процентов
  и уменьшается по мере роста истории.

Флаги запуска (их же печатает `/help`):

| Флаг | Действие |
|---|---|
| `--limit TOKENS` | другой лимит контекста модели (по умолчанию 130048) |
| `--fill WORDS` | наполнить историю заполнителем сразу после запуска |
| `--history PATH` | другой файл истории разговора |
| `--model NAME` | другая модель GigaChat (по умолчанию самая дешёвая, `GigaChat`) |
| `--log PATH` | другой журнал вызовов инструментов |
| `--http-log PATH` | другой HTTP-лог диалога с моделью |
| `--env PATH` | файл с ключом |
| `--no-cache` | переавторизоваться, минуя кэш токена |

Ключ `GIGACHAT_CREDENTIALS` берётся из того же `.env`, что и в прошлых задачах;
файл ищется от папки задачи вверх по дереву каталогов, `--env` перебивает поиск.

## Ловушки

* **API не сообщает лимит контекста заранее.** Единственный способ узнать,
  влезет ли история, — оценка плюс попытка. Поэтому оценка печатается рядом
  с фактом, а не вместо него.
* **`prompt_tokens` бывает не всем входом.** В каких-то запросах GigaChat
  отдаёт полный вход, в каких-то — только некэшированную часть, а
  `precached_prompt_tokens` не помогает: она не связана ни с длиной
  разговора, ни с размером текста. Поэтому «факт меньше оценки» в отчёте —
  не всегда ошибка формулы. Чтобы проверить формулу, берите шаги, где
  `cached` мал, а не медиану по всем.
* **`finish_reason: "length"` — обрезанный ответ.** Если ответ упёрся в потолок
  выхода, `completion_tokens` будет 8192 при любом смысле, а в историю
  попадёт мусор. Такой обмен только портит следующий запрос: его надо убрать
  (`/clear`) и переделать, а не считать по нему строки отчёта.
* **История — не бесплатная память.** Входные токены платятся за всю историю
  на каждом шаге цикла: два вызова инструмента в одном запросе платят
  за историю дважды. `/clear` — самый дешёвый способ сократить расход.
* **`/fill` на большом лимите — это дорого.** Заполнение отправляет модели
  запрос на десятки тысяч токенов. Для отладки формулы есть `/fill 5000`,
  а не `/fill`.
* **`precached_prompt_tokens` — кэш префикса промпта,** а не ответа:
  GigaChat ответы не кэширует, поэтому на цену ответа это не влияет.
  Поле `cached` в истории — именно этот счётчик; как длину префикса его
  читать нельзя.
* **`--limit` не меняет поведение модели.** Это только наша арифметика
  и процент в отчёте: модель по-прежнему откажет, если реальный контекст
  великоват, даже когда оценка говорит «влезает».
* **Заполнитель в истории — это настоящий обмен.** Он остаётся в разговоре
  и уходит модели в следующих запросах; `/clear` стирает и его.
* **`readme_words` читает README своей задачи.** Файл `w2t3/README.md` —
  не только документация, но и источник слов для инструмента: если он
  переименован или сильно сокращён, инструмент честно отвечает ошибкой
  «В README.md только N разных слов» — текст не выдумывается.
* **`fetch_url` не исполняет JavaScript.** В стандартной библиотеке нет
  браузерного движка: страница, которая отдаёт пустой каркас и грузит текст
  скриптом, вернёт «Текст не найден». Это ограничение метода, а не ошибка.
* **`fetch_url` не ограничен по размеру, и это опасно для чужих адресов.**
  Адрес приходит в инструмент из ответа модели, а модель можно попросить
  прочитать что угодно — включая локальные файлы. В учебном агенте на своей
  машине это удобно; для агента без присмотра человека нужен список
  разрешённых доменов и каталогов, иначе `file://` — это чтение любого
  файла с правами программы.
* **Текст страницы остаётся в истории.** Обмены с `fetch_url` переносят
  в контекст не только запрос и ответ, но и весь прочитанный текст: пара
  «просьба вызвать функцию — результат» (константа `PERSISTED_TOOLS`).
  Это сделано для исследования и стоит дорого: страница платится входными
  токенами в каждом следующем запросе, а не только в своём. На реальном
  разговоре из 39 обменов сохранённые страницы дали 99% истории (301 130
  токенов против 6 286 у пар «запрос–ответ»), то есть история стала больше
  лимита модели уже после трёх больших статей. Вернуть экономный вариант —
  убрать имя инструмента из `PERSISTED_TOOLS`; остальные инструменты
  (`roll_dice`, `current_time`, `readme_words`) в историю по-прежнему
  не попадают.
* **Сохранённые шаги живут в файле всей истории.** `/limits` показывает их
  отдельной строкой «сохранено в контексте» по каждому обмену и итогом
  внизу: столько платится в каждом запросе, пока не сделан `/clear`.
